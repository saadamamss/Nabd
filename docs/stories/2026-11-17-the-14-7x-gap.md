# The 14.7× Gap: How We Closed It in One Day

*A LinkedIn learning story — Nabd, 2026-11-17. Every number in this post was measured, not estimated.*

---

## The project

**Nabd** is an industrial IoT telemetry platform: devices (fridges, freezers, cold rooms) publish sensor readings over MQTT, a pipeline validates and stores them in TimescaleDB, and a rules engine turns thresholds into alerts — bilingual (Arabic/English), tenant-isolated, built to be trusted with food safety data.

The stack: **.NET 10 · EMQX (MQTT broker) · TimescaleDB/Postgres · RabbitMQ** — built with an AI pair-programmer, on a single 8-core development laptop. Not a lab cluster. A laptop. That constraint is part of the story.

## The goal

One number defines the product's core claim (**NFR-01**):

> **Sustain 2,000 readings/sec end-to-end** — 100 devices × 20/s + 20 devices × 1/s, for 10 straight minutes, with **zero loss**: every message the broker acknowledges must land in the database, exactly once.

2,000/s is the difference between a demo and a system. Below it, real deployments don't fit. We gave ourselves zero margin on purpose: the acceptance test requires **stored == delivered**, so a single lost message fails the run.

## The problem

The first honest load run measured it: **136 rows/s stored** while devices offered 1,852/s.

A **14.7× gap**. Not a slow database. Not a weak machine. Just a gap between what our pipeline claimed and what it did — and we refused to ship a system that had one.

## The fixing journey — issue → fix, all in one day

**1. The per-message tax → the batching lever.**
Every message paid its own toll: one round-trip to resolve the device's tenant, one to resolve its channels, one single-row INSERT, one commit, one ack. Fix: accumulate a batch, resolve the whole device set in **one** round-trip, fire **one** multi-row INSERT, commit **once**, then acknowledge everything that commit covers. One flush = one INSERT = one commit = a fleet of acks.

**2. The broker started killing connections → sharding.**
MQTT flow control limits unacknowledged in-flight messages *per connection*. Our single consumer kept stalling the connection, and EMQX dropped it under load. Fix: **4 consumer connections × in-flight window 200** (aggregate 800), evenly balanced by the queue — measured afterwards: 300,023–300,035 rows per shard. We didn't make one consumer faster; we stopped giving the broker a reason to choke it.

**3. Still slow: 716/s → the overlapping ack window.**
The pump now waited for every acknowledgment **before** starting the next batch — re-introducing the round-trip cost the lever had just removed. Fix: after the commit lands, launch the acks and **return immediately** — acks of batch *N* fly while batch *N+1* is already being built. Flush time dropped from ~1,100 ms to **10–31 ms**. The iron law stayed intact: *never acknowledge a message whose durable outcome did not commit* — early acks are how you lose data silently.

**4. The plot twist → we convicted the harness, not the machine.**
Progress stalled, so we split the CPU pie per process (`pidstat`): our **120 simulator processes were burning 427% of 8 cores** in scheduler overhead while the broker idled on one core, and a single-threaded Docker proxy was carrying all broker traffic. The "weak laptop" was never the bottleneck — the *measuring instrument* was. Fix: 12 processes × 10 devices, and a direct connection to the broker's container IP.

**5. The referee itself was lying → the window law.**
With drain accounted *inside* the 600 s window, the rate math capped at 1,924/s: **a mathematically perfect run could never pass**. Fix: END = fleet stop, drain measured after it (bounded, asserted small), rate = (window + tail) ÷ flight. Don't loosen the bar — fix the instrument until a perfect run *can* pass it, then let it judge.

**6. The near-miss: 1,998.5/s with 100% delivery → the grid anchor.**
Official run #1 failed by **0.075%** — while delivering 100.0000% of everything published. The arithmetic found it: each device's publish schedule anchored at its own connect time (~0.45 s late), so the fleet undershot its own target by exactly 905 messages. The pipeline was innocent. Fix: one shared epoch for the whole fleet (`--start-epoch`), kill time computed *from* that epoch.

**7. Official run #2 → GREEN.**

| | |
|---|---|
| Sustained rate | **2,000.2 rows/s** × 600 s |
| Delivery | **100.0000%** — stored 1,200,119 == delivered |
| Duplicates / rejects / broker drops | **0 / 0 / 0** |
| Latency | p50 **10 ms** · p99 **30 ms** |
| CPU headroom | pipeline 28% · broker 84% (of one core) · DB 40% |

Every one of the 22 messages "missing" from the ledger at fleet-kill was reconciled per-device: delivered-but-unacknowledged at the boundary, covered by QoS 1 redelivery. Zero unexplained rows. **The 14.7× gap closed in a day — by removing our own round-trips, not by buying hardware.**

**8. The bonus proof — revocation under load.**
Security is a number too. We minted a throwaway device through the real API, revoked its token mid-flight, and measured how fast the system stopped trusting it: **data plane 1.4 s** (storage stops instantly), **broker plane 43.4 s** (bounded by the authorization cache's 60 s TTL — worst case, by design), **reconnect refused instantly**. Detection ≤ 60 s: met.

## The decisions that made the difference

- **Honesty as acceptance criteria.** stored == delivered, zero margin. One lost message fails the run — that's the correct shape of the requirement, not a flaw in it.
- **Explain the arithmetic before re-running.** Every failure was reconciled line by line, to the last byte, before any fix was attempted. No "try again until green."
- **Measure the instrument like the system.** The biggest wins came from pidstat forensics on the *harness*, not from touching production code.
- **Fail-shut security.** Revocation was re-measured through the real API doors only — because a shortcut through the database would have measured a path production never exercises.

## What I'd tell any builder

Your bottleneck is rarely where you're looking. Ours wasn't the database, wasn't the broker, wasn't the laptop — it was per-message round-trips in our own code, then our own test harness, then our own acceptance math. Measure everything, reconcile every delta, and let the numbers convict you before the users do.

**From 136/s to 2,000.2/s. Zero loss. One day. One laptop. Zero hardware purchases.**
